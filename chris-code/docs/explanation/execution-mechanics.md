# Execution mechanics

`subagent-driven-development` is where a plan becomes code, and most of its design exists to solve two problems that show up the moment you drive real work through subagents: the orchestrator's context fills with noise, and a controller that loses its place re-does finished work. These mechanics — several backported from superpowers v6.0.0 and adapted to chris-code's agent layer — are how it stays lean and recoverable.

## Staged parallelism

Tasks aren't dispatched flat-sequential (slow) or flat-parallel (collisions). Instead the orchestrator **maps each task's file footprint up front** — every source and test file it will touch — and groups tasks into stages where everything in a stage has zero file overlap. Within a stage, subagents run concurrently; between stages, it waits for every task to commit or park, and settles the parked ones with one batched question before starting the next. Each task's stage and footprint is recorded with `ledger.py stage`, which refuses a path another unfinished task in the same stage already claims, so the map is checked rather than remembered and survives compaction.

The common serialization triggers are two tasks editing the same shared module or the same test file (`conftest.py`, `lib.rs`), or a later task depending on a type an earlier one introduces. When in doubt, it serializes — the cost of a conflict is higher than the cost of waiting. This is what lets chris-code treat parallelism as a feature rather than the footgun superpowers warns against.

## File handoffs

Anything pasted into a dispatch, and anything a subagent prints back, stays resident in the orchestrator's context for the rest of the session. So nothing is pasted. Artifacts are handed over as **files**, all under one resolved store directory, per-worktree and untracked, resolved by `ledger.py store-dir` — the single authority for the store path. The default is `.sdd/` at the repo toplevel: `git rev-parse --show-toplevel` resolves per-worktree, and `store-dir` seeds a `.gitignore` containing `*` inside the directory so the store ignores itself, with no edit to the repo's own ignore rules. A `--store DIR` override relocates it when a session needs to; every subcommand except `diff-since` and `labels` accepts the flag.

- **The task brief** is a *reference sheet*, not a restatement of the spec. `task_brief.py` extracts the plan's task entry — its actions, its `Consumes:` pointers, its spec §-references — to a file, embeds the intent and the task's notes from the store (see Run notes, below), logs their delivery, and always appends the shared-shapes section (see Cross-task pattern ledger, below). It fails loudly — non-zero exit, no file written — on a missing/empty intent, a stale `Consumes:` pointer, a missing or placeholder `Cases:` line, a `Cases:` row that states no result, an unanswered `open:` row, or a `Verify:` line with no backticked command. The dispatch then carries only pointers: where the task fits, the brief path, the spec path (the coder reads the referenced sections itself), the verbatim global constraints, the report-file path, the record path, and the scripts path (so the agent can run `ledger.py check` on its own record before returning).
- **Cross-task context** the coder can't recover by reading — a dependency contract (`built in Task 3 → path`), a conflict adjudication, a code entry point — is filed in the store as a task-note for the task that needs it, and reaches that task's brief as a terse pointer, never as dereferenced spec content.
- **The implementer's report** is written to its own file; the subagent returns only status, the changed-file list, a one-line test summary, and concerns.
- **The typed record** — every record-writing agent (coder, spec-reviewer, quality-reviewer, review-lite, and the research agent that writes a decision record) additionally writes a JSON record to a dispatch-supplied path before returning, then runs `ledger.py check` on it and fixes until it exits clean. This is the machine-readable channel the orchestrator queries instead of scanning prose for sentinels — see Durable progress ledger and Cross-task pattern ledger, below.
- **Reviewers** get file paths (brief, report, changed files, record) plus the verbatim constraints, and read the actual code. Diffs are never pasted.

Seen whole, the artifacts form **two chains with different consumers**. The markdown artifacts — brief → report → verdict — are the *reasoning chain*, flowing **between agents** by path: reviewers read the coder's report, a re-dispatched coder reads the reviewer's findings in the reviewer's own words, and the orchestrator holds only the pointers. The JSON records are the *decision chain*, flowing **to the orchestrator** through `ledger.py` queries: statuses, `duplication_pending`, `cannot_verify`, shared shapes — everything control flow consumes, validated at write time so it can be trusted without defensive reading. Prose is for minds, records are for steering; the hub touches prose only at the few named adjudication moments below.

The one thing pointers can't capture is **intent** — the observable outcome the task must produce. A fresh subagent doesn't inherit your conversation, so the brief states the *why* explicitly while everything else is referenced. See [Context & dispatch](context-and-dispatch.md).

## Pre-flight plan review

Before Task 1, the plan is scanned **once** for internal conflicts (tasks that contradict each other or the constraints) and plan-mandated defects (anything the plan asks for that a reviewer would flag — a test that asserts nothing, verbatim duplication, a swallowed error), and for missing or thin `Cases:` lines (a row written as a principle, or a list that skips obvious siblings or boundary inputs, ships one reading at a time). Every `open:` row, which is a behavior the planner couldn't decide, joins the same question. For a plan written before `Cases:` rows stated results, the orchestrator proposes them, and once you approve, writes every answer into the plan file itself, since `task_brief.py` reads the plan and an approval left in conversation would still fail the brief. Findings are raised as a single batched question with the offending plan text, asking which governs. A clean scan proceeds silently. This catches design problems before they're built, rather than per-task mid-run.

## Durable progress ledger

Conversation memory does not survive compaction, and a controller that loses its place can re-dispatch finished tasks. So progress is tracked in the typed store, not only in the live task list. `ledger.py run-state` shows where the run stands (the stage map with each task's state and rounds, what's parked for you, notes owed, open disclosures and questions, agent handles, and the latest checkpoint); `ledger.py read` renders the whole store as markdown; `ledger.py open` lists what's still unresolved; `ledger.py completed` lists which task ids are done. When a task's gate has passed and its commit is in, the orchestrator appends a typed completion entry (`ledger.py append --type complete --task N --note "..."`) to the store's append-only log, which only `ledger.py` writes, under a lock, rather than a prose note the orchestrator would later have to pattern-match. The entry is refused unless `ready` passes and the commit matches the tree the gate checked. A task id `completed` lists is done — even if `open` still lists a `duplication_pending` entry for it; the pattern ledger deliberately carries that forward as assigned work for a later task, not as evidence this one is unfinished (see Cross-task pattern ledger, below). Any *other* open item on a completed task — a `cannot_verify`, an unresolved status, a malformed record — means the completion was premature; it's treated as unfinished and investigated before resuming past it. Before each pause or `/compact`, the orchestrator files a checkpoint note for what the store can't show (an interrupted agent, the next steps). After compaction, it re-resolves the scripts and store paths (neither survives compaction either), then rebuilds its task list from `ledger.py run-state`, `ledger.py open`, and `ledger.py completed`, trusting them and `git log` over its own recollection — finished tasks are never re-run.

## Run notes

The orchestrator is the one actor that sees the whole run, and what it knows across tasks used to live only in its context: a note owed to a later task, a test recipe every brief should carry, a changelog line some task must write, a question saved for the user, its own judgment calls. A long run outgrows that, and an orchestrator left to improvise keeps a free-form notes file that grows without bound, is never consumed, and silently drops items (a standing rule that falls out of later briefs, a note filed after its target's brief was built, a changelog debt nobody owns).

So that knowledge is typed entries in the store. `ledger.py note` files one of seven kinds: a **task-note** for one later task, a **run-note** for every task, a **disclosure** a task or the close owes the docs, a **question** for the user, a **follow-up** (optionally with the `--rule` it falls under, which `report` groups by), a **disposition** (a call the orchestrator made alone), and a **checkpoint** (what a resume can't derive). Each kind has one consumer and one end of life:

- `task_brief.py` embeds a task's task-notes, the active run-notes and the disclosures it owes, and logs the delivery. A note filed after the brief, including a run-note for a task already in flight, stays undelivered until the brief is rebuilt, the session delivers it (`notes --deliver`), or the orchestrator logs a waiver with its reason.
- `append --type complete` refuses a task with an undelivered note or an open disclosure or question it owns, and `close-round` refuses while any disclosure or question is open, so a debt reaches its owner before the run can finish.
- `ledger.py report` builds the completion report from the store: the user's rulings, the follow-ups, the coders' unlisted cases, the dispositions and waivers, and where each disclosure landed. `clear` refuses to delete open follow-ups, disclosures or questions without the user's confirmation.

The rule behind it is knowledge through files, authority at the orchestrator: only the orchestrator files notes, and subagents report cross-task items in their own records for it to file.

## Cross-task pattern ledger

Staged parallelism and file handoffs both work by keeping each coder's context small and disjoint — which is exactly what blinds a coder to what its siblings are doing. Four tasks that each need the same block of logic will each write it, and every per-task review passes, because no reviewer ever sees more than one diff. The orchestrator is the only actor that sees the whole task sequence, so acting on that duplication is its job alone — though the record-keeping itself is automatic: coders declare `new_shared_symbols` and `duplication_pending` directly in their typed record (see the coder agent's Typed record section) instead of a prose sentinel, and `ledger.py shapes` derives the shared-shapes list from those records on the fly.

Every brief `task_brief.py` produces carries that list unconditionally — the "Shared shapes already built" section, which no flag disables — so a later same-family task sees a shape the moment an earlier task declares it, with no manual carry step to forget. When a coder's record contains a `duplication_pending` entry (it copied a block because the file that should own the helper was outside its footprint), the entry surfaces in `ledger.py open`; the orchestrator assigns the hoist to the next task whose footprint covers that file, then resolves it (`ledger.py resolve <id> --note "..."`, `<id>` copied verbatim from `open`'s output — content-derived from the entry, not a positional index, so a rewritten record's entry gets a new id) once the hoist lands — rather than letting the copy ride to the whole-change commit gate. The spec-reviewer's ⚠️ "cannot verify from diff" line follows the identical open → ground → resolve loop: it lands in the record's `cannot_verify` field, surfaces in `ledger.py open`, and the orchestrator resolves it once grounded in the actual code (see Judging from compressed reports, below) — this isn't a duplication-only mechanic.

Planning gaps travel the same way. A coder that handles a case its brief's `Cases:` line didn't list reports it as a `concerns` entry starting `unlisted case:`. That marks a gap in the plan, not a problem with the task, so the orchestrator doesn't treat it as a concern to investigate. It carries the case forward as a task-note for any later task covering the same kind of rule, and `ledger.py report` lists every unlisted case beside the follow-ups when it claims completion. The plan itself is never edited mid-run; this is how its gaps surface instead.

This is the execution-altitude link in a longer chain: `lean-plan` grounds against existing code and names a shape several tasks will share as a contract with an owner; the typed store carries that contract between tasks; the coder mirrors by reference. The chain exists because coherence established when a change is whole does not survive decomposition unless it is deliberately carried — see [Coherent change](coherent-change.md#coherence-has-to-survive-decomposition).

## Fixed models per role

Each role runs on one model, pinned in its agent's frontmatter, and the orchestrator passes no override: coders and the `*-review-lite` gates run on sonnet; the spec, quality, design and intent reviewers, `mutation-tester`, `bug-hunter` and the `remediating-issues` research agent run on opus; `claim-checker` runs on haiku. An orchestrator choosing per dispatch drifted toward opus coders on a "design judgment" rationale, but design judgment now lives in the decision doc and the brief, so a coder implements choices already made. The one exception is the mutation tester at the `light` rigor level, which verification dispatches on sonnet, since a light change gets few breaks. A coder runs on opus only by the user's ruling, which the stage's batched question and a blocked coder both offer. A coder checks its own model before changing anything, and `ledger.py check` refuses a finished coder record above sonnet unless the ruling is logged for its task.

## Reviewer integrity

The gates are only as good as their independence, so several rules protect it:

- Reviewers are **read-only** and never mutate the tree.
- The orchestrator **never coaches a reviewer** to suppress, soften, or pre-rate a finding — no "don't flag X," no "at most Minor." If a dispatch contains that language, it's pre-judging to spare a review loop; the finding must be raised and adjudicated in the open.
- A reviewer's mandate is **never narrowed** to a subset of its remit ("just check for bugs," "only the parser"). Under-cueing the scope is as corrosive as suppressing a finding.
- **Plan-mandated defects are the user's call** — surfaced with the plan text, never silently fixed against the plan or silently shipped because the plan asked for it.

## Judging from compressed reports

The orchestrator decides what to integrate from *compressions* — a coder's report, a reviewer's verdict — one step removed from the evidence. It classifies each before acting: **fact-shaped** claims (did the suite pass?) it trusts; **judgment-shaped** verdicts (a cohesion call, a "cannot verify," a conflict) it does not integrate without grounding in evidence. A verdict you haven't grounded is an assertion laundered into a decision.

It grounds **by dispatch, not by reading**: opening the changed code itself would spend the very context the file handoffs protect, and the skipped re-read is invisible while the burned context is not. Instead the orchestrator turns the verdict into a *decidable claim* ("`process_data` now takes 8 parameters" is decidable; "this will be hard to maintain" is not) and dispatches `claim-checker` — one claim, a file and line range, and deliberately no verdict text, so the checker can't anchor on the conclusion it's checking. Back come `holds` / `does-not-hold` / `not-decidable-by-reading` plus 3–10 verbatim quoted lines. Evidence is mandatory — a bare verdict word would be one more laundering channel — and because quotation is not conclusion, the answer needs no grounding of its own: the chain terminates there. Grounding informs how a finding is acted on; it never overturns the reviewer's call. When a claim isn't decidable or the evidence spans tasks, the orchestrator escalates with the quoted lines attached, not a paraphrase. This is the integrator-side half of "Do Not Trust the Report" — see [The assurance model](the-assurance-model.md#the-integrator-is-the-unguarded-seam).

## The fix loop

A failed review starts a recursion: coder fixes, reviewers look again. An undisciplined recursion ping-pongs, because each patch triggers new findings and each round restates the last. The loop's rules came from classifying the fix cycles of real runs, and each one targets a failure that actually occurred there, not a hypothetical. The orchestrator makes no routing call anywhere in it. Reviewers tag, `ledger.py` computes the step, and the orchestrator makes the dispatch the script prints.

- **Verdicts accumulate before any triage.** The spec reviewer and quality reviewers are dispatched together, and no fix is dispatched while any of them is still out. A fix sent against a partial verdict set buys one guaranteed extra round when the late verdict lands. Triage runs once, and one fix dispatch carries every reviewer's record path.
- **Reviewers tag every finding; a script routes.** Each finding carries a `severity` (1 to 5), a `reach` (`local`: one site; `class`: the same rule at several sites in the task's files; `contract`: the fix changes a public API, a schema, or a symbol with consumers outside the task's files), the `rule` it breaks, stated as behavior, and its `sites`. `ledger.py triage` turns the tags into a tier, and nothing else decides it:

  | | reach `local` or `class` | reach `contract` |
  |---|---|---|
  | **S1-S2** | note | defer |
  | **S3-S5** | patch | holistic |

  A coder's `root cause:` concern is a holistic item, and so is a finding the coder raises to `contract` reach because its fix turned out to need a contract change. `recurring` and `introduced_by_fix` never change a tier. They oblige the next fix to list the flagged sites and they feed `stats`. The orchestrator never sorts findings into trivial and non-trivial, never re-rates a tag, and never closes a finding: only a re-check that stops raising it, or your ruling, does.
- **Two fix rounds, then you.** `triage` derives the next step from the records and logs it as an entry: a **patch** round when S3+ local or class findings are open, a **holistic** round when any holistic item is open, one **polish** dispatch when only notes remain, **done** when nothing does. After two patch or holistic rounds with work still open, the step is **escalate**, and the task parks. A task can't get a third round without your logged ruling, and a ruling round that leaves work open escalates again.
- **Notes ride along and are never re-reviewed.** S1-S2 findings go to the coder with the round's dispatch. The coder fixes each note or records it in `notes_skipped` with a reason, and either way it is handled and nobody re-reads it. Notes cost no review cycle, and none is dropped without you deciding at the close (see the deferrals bullet, below).
- **A holistic round is task-wide, researched once.** An opus research agent runs `remediating-issues`' per-task variant over the whole task: its diff, every reviewer record, and the coder's records. It may redo the task's implementation shape, and it writes one decision doc that accounts for every open finding and `root cause:` concern. Each fix choice's `cases` table gives every affected case its site, its named test and its expected result. The choice lists the couplings it touches, each of which must also be a case, and records the premise it rests on with the probe that confirmed it. The orchestrator never writes the doc, since its memory of the run is not research, and the doc is a typed record that `ledger.py check` verifies. The original sonnet coder then implements it case by case, mapping every case to a hunk (`decision_rows`). A decision doc is no longer written per finding: a doc per local fix cost a research dispatch on a one-site problem, and several per-finding docs on one task produced incoherent designs.
- **A fix closes every site of its rule, and says where.** In a patch or ruling round the coder states each finding's rule and searches the task's files plus the consumers of every symbol its fix changes. It lists every site where the rule applies as a row, each mapped to the hunk that fixes it or marked `already correct` with evidence, and a `recurring` or `introduced_by_fix` finding's flagged sites must appear as rows. The sweep records its evidence, either `searched` (the command and its result) for a rule text can express, or `inspected` (what was examined and how it was found) for one it can't. A site outside the task goes in `sites_outside` and routes to the close. `ledger.py check` verifies that every sent finding is covered exactly once and that every row's hunk overlaps the fix diff, so a partial build can't be claimed complete.
- **Tests come first.** For each S3+ finding the coder writes a test, runs it, and records the command and its failing output before the fix. A finding with no new test to write gets `n/a` with a category from a closed list (`structural`, `docs`, `unreachable`, `existing`) and a reason. Reviewers judge the reason, and `stats` counts the categories so overuse is visible. A fix that edits an assertion in a pre-existing test, deletes a test or an assertion, or adds a skip marker needs a `test_changes` entry saying why, so the shortcut of bending the test to fit the code is visible.
- **Undefined behavior follows precedent.** When the brief leaves a behavior open, the coder doesn't stop. It picks what the codebase already does for the nearest analogous case, implements it, and records an `open` entry: the question, the choice, and the `precedent` site, or `no precedent` with its reasoning. Reviewers don't raise a finding against a declared choice for disagreeing with it, only when it contradicts an existing precedent. A contract change the plan didn't specify is recorded the same way. Open choices join the stage's batched question with the coder's choice as the default, so accepting costs nothing, and overriding is a ruling: it starts a ruling round, which the spec reviewer re-checks, even when the task had reached `done`.
- **A wrong finding is contested, not fixed.** The coder records `contested` with a reason (`wrong` or `plan-conflict`) and its evidence instead of fixing. At re-check the raising reviewer gets the evidence and answers each contest in its record with `concede` or `hold` and a reason. A concede closes the finding, a hold parks the task for you, and `check` refuses a re-check record that leaves a contest unanswered, so a finding closes only after someone read the evidence. A contest is settled in the round's re-check; it never starts a round of its own. A finding that was conceded, waived or ruled is settled, and a reviewer that raises it again must mark it `reopens` with a site in lines changed since, which `check` verifies.
- **Re-checks go only to the reviewers `triage` names.** After a patch or ruling round, the reviewers whose S3+ findings were sent re-check the fix diff and the consumers of every symbol it changed, and a gate finding re-runs the gate instead of dispatching anyone. After a ruling round that sent no finding (an override), the spec reviewer re-checks. After a holistic round every reviewer re-checks the whole task. After a polish nobody does, since the gate is its check. Re-reading unchanged code resampled it into fresh nits, and real bugs concentrate in the fix and its callers.
- **Fixes must not regress.** The fix goes back to the original coder via `SendMessage` while that agent is reachable, so it keeps its context. Each coder's agent id is recorded with `ledger.py handle`, so `run-state` still names it after a compaction. Before each fix, `ledger.py snapshot --task N --label ...` records the working tree as a baseline, because the earlier work is still uncommitted and would otherwise be indistinguishable from the fix. The coder reads its round from `ledger.py baseline <tree> --task N`, which prints the round's kind, who re-checks it, the decision doc path for a holistic round, and the findings sent, and `check` refuses a finished fix whose last triage entry before its baseline isn't a fix round, or whose baseline an earlier cycle used. Against that baseline (`diff-since`, limited to the task's own files) the record must map every changed hunk to the finding or choice it implements (`hunk_map`), list the consumers it verified for every symbol it changed (`consumers_checked`), and from cycle 2 carry a `diagnosis` (root cause, end-state, why the findings resolve as a cluster). Reviewers list what the fix broke in `introduced_by_fix`. A consumer the coder can't change itself (another language) comes back as `done_with_concerns` and is fixed by that language's coder as part of the same task. A fix that needs a public-API change stops before making it and records `reach_raised`, and the next triage makes the task holistic. A first attempt that makes a contract change the plan didn't specify records it as an open choice instead. Comments must state behavior, not the review process, and `ledger.py labels` scans added lines for task and finding ids, cycle numbers and commit hashes. The gate and `check` run it, so a leaked label can't be skipped past.
- **A root cause outside the brief is a holistic item.** The coder reports it as a `root cause:` concern starting with the site, and `triage` routes it to a holistic round, where the research agent decides with evidence whether this task fixes it or files it. A decision that lists it in `excluded` defers it: `triage` files it once as a follow-up with the reason and stops counting it. A finding the decision escalates is contested by the coder with the decision's evidence, so the raising reviewer concedes it or holds it for you. The user can also waive a root cause at the stage batch. The task's footprint is its latest `ledger.py stage` files, and `check` refuses a `root cause:` path or a `sites_outside` entry inside it, so a deferral can't point at the task's own code.
- **Park, then one question per stage.** A task parks when triage escalates, when a reviewer holds a contest, or when `ready` finds an open behavior choice or a contract change needing approval. A parked task doesn't commit, and the rest of its stage keeps going. Once no task in the stage has a dispatch in flight, the orchestrator sends one message covering every parked item: each task's open findings (rule and sites) with the holistic decision's choice and its rejected alternatives where one ran, the round history with each round's closed and introduced counts, every open choice with the coder's default and its precedent, and a recommended answer for every item. One reply settles the batch: "accept all", or overrides by item number. You can rule a fix (on an opus coder if you say so), waive a finding, uphold or dismiss a held one, accept or override an open choice, or approve a contract change, and each answer is logged as a `user ruling:` on its item. A task coming back after a failed ruling round always offers "land as-is and file the rest as follow-ups" next to another ruling, and the recommendation picks between them by whether the last round closed more findings than it introduced.
- **The commit path is scripted.** When triage says `done`, `ledger.py ready` lists everything that still stops the commit: a held finding, an open behavior choice, an undelivered note, an open `cannot_verify`, a malformed record, and at `final` an open escalation. When it passes, the orchestrator stages exactly the task's files and runs `ledger.py gate --task N --test "<the task's Verify command>"`, which runs labels on the staged lines, then lint, then the task's `Verify:` command, each passing only on exit 0. A labels or lint failure goes back to the coder as the same attempt and consumes no round. A test failure becomes an S3 local gate finding over the task's files and enters triage like any other. After a passing gate the orchestrator commits and runs `append --type complete`, which re-runs `ready` and checks the commit matches the tree the gate passed. This replaces a per-task review-lite pass, which re-reviewed what the reviewers had approved. Its two unique checks moved to the quality reviewers (the project's CLAUDE.md constraints, and public sentinel returns).
- **The whole-change gate uses the same triage.** After the last stage, `*-review-lite` reviews the whole `BASE..HEAD` diff and tags its findings, marking `contract` any symbol the diff shows as public. `triage --task final` routes them, with the same two-round bound and the same gate before each fix commit. Lite then re-reviews over a package of just the fix commit after a patch, or the full diff after a holistic round.
- **Deferrals reach you once, at the close.** `triage` files each deferral exactly once as a follow-up carrying its rule: S1-S2 contract-reach findings, notes a coder skipped, and sites a sweep found outside the task. An outside site goes as a task-note when a later task's footprint covers it, otherwise as a follow-up. The completion report groups the open follow-ups by rule as one batch, and for each item you pick fix, file or ignore. The fix items go through `remediating-issues`' Batch Path as one change.
- **The check history.** A record is overwritten each cycle, so a passing `ledger.py check` on a record in the store appends a one-line summary to the store's `history.jsonl`. `ledger.py stats` reads it back: each task's verdicts cycle by cycle, each triage round with its kind, the coder model and how many findings it closed, saw survive and saw a fix introduce, and the tests-first `n/a` counts by category.
- **Cases are decided in the plan, not discovered in review.** Coders patched the line a finding cited, and siblings like `size=None` then surfaced one review cycle at a time, because no one had written the case family down. Each plan task's `Cases:` line now states behavior as rows, each with its situation and expected result (`size=0 → ValueError`), never as a principle ("validate sizes"). A behavior the planner can't decide is an `open:` row, which pre-flight puts to you before the build. The task's `Verify:` line is a backticked command where exit 0 means pass, and it is the command the gate runs. `task_brief.py` refuses a task with a row that has no result, an unanswered `open:` row, or no `Verify:` command. The spec reviewer checks that each listed row has a test with the listed result, and a finding that names a listed row is S3 or higher.
- **Rigor scales with the project.** `scripts/rigor.py` resolves a level, `light`, `standard` or `heavy`, from the repo: under 5,000 counted source lines is `light`, 5,000 to 30,000 is `standard`, and more is `heavy`. A language binding (pyo3, maturin, napi and the like) raises the level to at least `standard`, and numeric or ML dependencies raise it one step. A `Test rigor: <level>` line in the repo's `CLAUDE.md` overrides all of this. A plan task's `Rigor:` line can raise that task, never lower it. Every brief states its level with the reasons, and each role applies its row of `subagent-driven-development/rigor.md`: how many cases the plan writes, which missing cases a reviewer rates S3, and how many breaks the mutation tester makes and which survivors gate. A small project gets realistic cases and a few breaks. A large one keeps today's depth. At every level a test that can't fail is S3, and a `Cases:` row is never optional.
- **Light path.** `executing-plans` is the path for small work and runs none of this triage. It builds the same briefs and the quality reviewers still review, at most two fix rounds precede a question to you, and each commit goes through `gate`, `ready --light` and `complete --light`. `--light` skips only the triage, held and open-choice checks and is recorded on the completion entry, so `report` shows which tasks ran light. The whole-change review stays on review-lite.

Round count alone is the wrong metric for this loop, since a re-check on a changed surface legitimately catches real regressions. The waste metric is narrower: rounds where a fix failed to close its own finding, or where a finding was available earlier but delivered late. The rules above target exactly those, and `stats` reports closed, survived and introduced counts per round so they can be measured.

Records carry schema version 2. A store left by an earlier release is refused with a message to finish that run on the release that started it, or to clear it with `ledger.py clear` and start over.

## The close round

The completion close (`verification-before-completion`) has its own loop, and before this rule it was the ungoverned one. Its gates (design review, intent re-check, mutation) ran one at a time with a fix after each, so a design fix was followed by intent findings on the patched code, then mutation findings, and every behavioral fix reopened the gates before it. Those fixes also skipped the coherence engine entirely.

A **close round** dispatches every applicable gate at once, waits for all of them, and triages once. Trivial findings are fixed inline. A discriminating-test fix for a mutation finding goes straight to the coder. Separable improvements are filed as follow-up notes. The non-trivial set goes through `remediating-issues`' close-gate variant as one batch: one consolidated research pass and decision doc, which pauses for your approval (unlike the per-task variant, which runs continuously), then straight to one `lean-plan` (no `lean-spec`, since the gate reports already say what is wrong) and SDD on the same store. Round 2 re-runs only what the remediation could have changed: the design reviewers at their same report paths (so each judges whether its prior findings were addressed instead of re-deriving the whole change), mutation over the remediation's range only, and the intent re-check only when the remediation changed behavior. A new finding on code the remediation never touched counts as fresh sampling, not a regression, and is filed as a follow-up note. Whatever non-trivial work survives round 2 goes to the user. `ledger.py close-round --expect N` keeps the count as a typed entry and refuses a third round, so the cap survives compaction. `--expect` also fails when the store disagrees with the round you think you're starting, so a store left by an earlier run can't silently start a new close at round 2.
