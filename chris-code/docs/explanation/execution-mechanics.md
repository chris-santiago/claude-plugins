# Execution mechanics

`subagent-driven-development` is where a plan becomes code, and most of its design exists to solve two problems that show up the moment you drive real work through subagents: the orchestrator's context fills with noise, and a controller that loses its place re-does finished work. These mechanics — several backported from superpowers v6.0.0 and adapted to chris-code's agent layer — are how it stays lean and recoverable.

## Staged parallelism

Tasks aren't dispatched flat-sequential (slow) or flat-parallel (collisions). Instead the orchestrator **maps each task's file footprint up front** — every source and test file it will touch — and groups tasks into stages where everything in a stage has zero file overlap. Within a stage, subagents run concurrently; between stages, it waits for all reviews to pass before starting the next.

The common serialization triggers are two tasks editing the same shared module or the same test file (`conftest.py`, `lib.rs`), or a later task depending on a type an earlier one introduces. When in doubt, it serializes — the cost of a conflict is higher than the cost of waiting. This is what lets chris-code treat parallelism as a feature rather than the footgun superpowers warns against.

## File handoffs

Anything pasted into a dispatch, and anything a subagent prints back, stays resident in the orchestrator's context for the rest of the session. So nothing is pasted. Artifacts are handed over as **files**, all under one resolved store directory, per-worktree and untracked, resolved by `ledger.py store-dir` — the single authority for the store path. The default is `.sdd/` at the repo toplevel: `git rev-parse --show-toplevel` resolves per-worktree, and `store-dir` seeds a `.gitignore` containing `*` inside the directory so the store ignores itself, with no edit to the repo's own ignore rules. A `--store DIR` override relocates it when a session needs to; every subcommand except `diff-since` accepts the flag.

- **The task brief** is a *reference sheet*, not a restatement of the spec. `task_brief.py` extracts the plan's task entry — its actions, its `Consumes:` pointers, its spec §-references — to a file, embeds the intent and any cross-task notes, and always appends the shared-shapes section (see Cross-task pattern ledger, below). It fails loudly — non-zero exit, no file written — on a missing/empty intent a stale `Consumes:` pointer, or a missing or placeholder `Cases:` line. The dispatch then carries only pointers: where the task fits, the brief path, the spec path (the coder reads the referenced sections itself), the verbatim global constraints, the report-file path, the record path, and the scripts path (so the agent can run `ledger.py check` on its own record before returning).
- **Cross-task context** the coder can't recover by reading — a dependency contract (`built in Task 3 → path`), a conflict adjudication, a code entry point — is added to the brief as terse pointers, never as dereferenced spec content.
- **The implementer's report** is written to its own file; the subagent returns only status, the changed-file list, a one-line test summary, and concerns.
- **The typed record** — every record-writing agent (coder, spec-reviewer, quality-reviewer, review-lite) additionally writes a JSON record to a dispatch-supplied path before returning, then runs `ledger.py check` on it and fixes until it exits clean. This is the machine-readable channel the orchestrator queries instead of scanning prose for sentinels — see Durable progress ledger and Cross-task pattern ledger, below.
- **Reviewers** get file paths (brief, report, changed files, record) plus the verbatim constraints, and read the actual code. Diffs are never pasted.

Seen whole, the artifacts form **two chains with different consumers**. The markdown artifacts — brief → report → verdict — are the *reasoning chain*, flowing **between agents** by path: reviewers read the coder's report, a re-dispatched coder reads the reviewer's findings in the reviewer's own words, and the orchestrator holds only the pointers. The JSON records are the *decision chain*, flowing **to the orchestrator** through `ledger.py` queries: statuses, `duplication_pending`, `cannot_verify`, shared shapes — everything control flow consumes, validated at write time so it can be trusted without defensive reading. Prose is for minds, records are for steering; the hub touches prose only at the few named adjudication moments below.

The one thing pointers can't capture is **intent** — the observable outcome the task must produce. A fresh subagent doesn't inherit your conversation, so the brief states the *why* explicitly while everything else is referenced. See [Context & dispatch](context-and-dispatch.md).

## Pre-flight plan review

Before Task 1, the plan is scanned **once** for internal conflicts (tasks that contradict each other or the constraints) and plan-mandated defects (anything the plan asks for that a reviewer would flag — a test that asserts nothing, verbatim duplication, a swallowed error), and for missing or thin `Cases:` lines (a list that skips obvious siblings or boundary inputs ships one case at a time). For a plan written before `Cases:` lines existed, the orchestrator proposes them, and once you approve, writes them into the plan file itself, since `task_brief.py` reads the plan and an approval left in conversation would still fail the brief. Findings are raised as a single batched question with the offending plan text, asking which governs. A clean scan proceeds silently. This catches design problems before they're built, rather than per-task mid-run.

## Durable progress ledger

Conversation memory does not survive compaction, and a controller that loses its place can re-dispatch finished tasks. So progress is tracked in the typed store, not only in the live task list. `ledger.py read` renders the whole store as markdown; `ledger.py open` lists what's still unresolved; `ledger.py completed` lists which task ids are done. When a task's reviews come back clean, the orchestrator appends a typed completion entry (`ledger.py append --type complete --task N --note "..."`) — the store's only append-only file, written by the orchestrator alone — rather than a prose note the orchestrator would later have to pattern-match. A task id `completed` lists is done — even if `open` still lists a `duplication_pending` entry for it; the pattern ledger deliberately carries that forward as assigned work for a later task, not as evidence this one is unfinished (see Cross-task pattern ledger, below). Any *other* open item on a completed task — a `cannot_verify`, an unresolved status, a malformed record — means the completion was premature; it's treated as unfinished and investigated before resuming past it. After compaction, the orchestrator re-resolves the store path (it doesn't survive compaction either), then rebuilds its task list from `ledger.py read`, `ledger.py open`, and `ledger.py completed`, trusting them and `git log` over its own recollection — finished tasks are never re-run.

## Cross-task pattern ledger

Staged parallelism and file handoffs both work by keeping each coder's context small and disjoint — which is exactly what blinds a coder to what its siblings are doing. Four tasks that each need the same block of logic will each write it, and every per-task review passes, because no reviewer ever sees more than one diff. The orchestrator is the only actor that sees the whole task sequence, so acting on that duplication is its job alone — though the record-keeping itself is automatic: coders declare `new_shared_symbols` and `duplication_pending` directly in their typed record (see the coder agent's Typed record section) instead of a prose sentinel, and `ledger.py shapes` derives the shared-shapes list from those records on the fly.

Every brief `task_brief.py` produces carries that list unconditionally — the "Shared shapes already built" section, which no flag disables — so a later same-family task sees a shape the moment an earlier task declares it, with no manual carry step to forget. When a coder's record contains a `duplication_pending` entry (it copied a block because the file that should own the helper was outside its footprint), the entry surfaces in `ledger.py open`; the orchestrator assigns the hoist to the next task whose footprint covers that file, then resolves it (`ledger.py resolve <id> --note "..."`, `<id>` copied verbatim from `open`'s output — content-derived from the entry, not a positional index, so a rewritten record's entry gets a new id) once the hoist lands — rather than letting the copy ride to the whole-change commit gate. The spec-reviewer's ⚠️ "cannot verify from diff" line follows the identical open → ground → resolve loop: it lands in the record's `cannot_verify` field, surfaces in `ledger.py open`, and the orchestrator resolves it once grounded in the actual code (see Judging from compressed reports, below) — this isn't a duplication-only mechanic.

Planning gaps travel the same way. A coder that handles a case its brief's `Cases:` line didn't list reports it as a `concerns` entry starting `unlisted case:`. That marks a gap in the plan, not a problem with the task, so the orchestrator doesn't treat it as a concern to investigate. It carries the case forward as a cross-task note in the brief of any later task covering the same kind of rule, and lists every unlisted case with the follow-ups when it claims completion. The plan itself is never edited mid-run; this is how its gaps surface instead.

This is the execution-altitude link in a longer chain: `lean-plan` grounds against existing code and names a shape several tasks will share as a contract with an owner; the typed store carries that contract between tasks; the coder mirrors by reference. The chain exists because coherence established when a change is whole does not survive decomposition unless it is deliberately carried — see [Coherent change](coherent-change.md#coherence-has-to-survive-decomposition).

## Reviewer integrity

The gates are only as good as their independence, so several rules protect it:

- Reviewers are **read-only** and never mutate the tree.
- The orchestrator **never coaches a reviewer** to suppress, soften, or pre-rate a finding — no "don't flag X," no "at most Minor." If a dispatch contains that language, it's pre-judging to spare a review loop; the finding must be raised and adjudicated in the open.
- A reviewer's mandate is **never narrowed** to a subset of its remit ("just check for bugs," "only the parser"). Under-cueing the scope is as corrosive as suppressing a finding.
- **Plan-mandated defects are the user's call** — surfaced with the plan text, never silently fixed against the plan or silently shipped because the plan asked for it.

## Judging from compressed reports

The orchestrator decides what to integrate from *compressions* — a coder's report, a reviewer's verdict — one step removed from the evidence. It classifies each before acting: **fact-shaped** claims (did the suite pass?) it trusts; **judgment-shaped** verdicts (a cohesion call, a "cannot verify," a conflict) it does not integrate without grounding in evidence. A verdict you haven't grounded is an assertion laundered into a decision.

It grounds **by dispatch, not by reading**: opening the changed code itself would spend the very context the file handoffs protect, and the skipped re-read is invisible while the burned context is not. Instead the orchestrator turns the verdict into a *decidable claim* ("`process_data` now takes 8 parameters" is decidable; "this will be hard to maintain" is not) and dispatches `claim-checker` — one claim, a file and line range, and deliberately no verdict text, so the checker can't anchor on the conclusion it's checking. Back come `holds` / `does-not-hold` / `not-decidable-by-reading` plus 3–10 verbatim quoted lines. Evidence is mandatory — a bare verdict word would be one more laundering channel — and because quotation is not conclusion, the answer needs no grounding of its own: the chain terminates there. Grounding informs how a finding is acted on; it never overturns the reviewer's call. When a claim isn't decidable or the evidence spans tasks, the orchestrator escalates with the quoted lines attached, not a paraphrase. This is the integrator-side half of "Do Not Trust the Report" — see [The assurance model](the-assurance-model.md#the-integrator-is-the-unguarded-seam).

## The fix loop

A failed review starts a recursion — coder fixes, reviewers re-review — and an undisciplined recursion ping-pongs: each patch triggers new findings, each round restates the last. The loop's mechanics came from measuring a real 25-round wave, and each rule targets a failure that actually occurred there, not a hypothetical:

- **Verdicts accumulate before any fix.** The spec reviewer and quality reviewers are dispatched together, and no fix is dispatched while any of them is still out; one fix dispatch carries every reviewer's record path. (A fix sent against a partial verdict set buys one guaranteed extra round when the late verdict lands. Running spec review first had the same effect structurally: its fix landed, then quality's findings arrived as a second round.)
- **Non-trivial findings are remediated, not patched.** The batch is triaged once. A trivial finding (no behavior change, one site, no contract: a docstring, message text, local rename, lint) goes straight to the coder. A finding that only reports a case the plan's `Cases:` line already lists also goes straight to the coder, since the plan decided it. Anything else goes first through `remediating-issues`' per-task variant, which researches the task's footprint once and writes one decision doc with a defended choice per finding. The coder then fixes against that doc. It is decision-only with no approval pause, so execution stays continuous.
- **Fixes must not regress.** A fix used to run the same workflow as the first implementation, aiming only to make the listed findings disappear. It ran in a cold agent, and it was checked by a narrower list than the reviewer would apply. That is how fixes introduced new issues. Now the fix goes back to the original coder via `SendMessage` while that agent is reachable, so it keeps its context. The coder self-reviews the fix against the quality reviewer's own checklist. Before each fix, `ledger.py snapshot` records the working tree as a baseline, because the cycle-1 work is still uncommitted and would otherwise be indistinguishable from the fix. Against that baseline (`diff-since`, limited to the task's own files, since the other tasks in a stage edit the same working tree), the coder's record must map every changed hunk to the finding or choice it implements (`hunk_map`) and list the consumers it verified for every symbol it changed (`consumers_checked`). Reviewers judge the actual fix diff and list what the fix broke, on its own lines or in a consumer, in `introduced_by_fix`, a failed-fix signal like `recurring`. A consumer the coder can't change itself (another language, or a public-API change) comes back as `done_with_concerns` naming it. A cross-language consumer is then fixed by that language's coder as part of the same task, under its own record, with its quality reviewer added to the re-review set; a public-API change escalates to you. Comments must state behavior, not the review process: coders copy the run's vocabulary (task and finding ids, cycle numbers, decision docs, commit hashes) into comments, and a self-check grep shares its author's blind spot, so `ledger.py labels` scans the added lines. Coders run it before reporting, and the orchestrator runs it again when a coder returns, before review, sending any hit back as the same attempt so a leaked label never costs a review cycle.
- **The check history.** A record is overwritten each cycle, so a passing `ledger.py check` on a record in the store appends a one-line summary to the store's `history.jsonl`. `ledger.py stats` reads it back: each task's verdicts cycle by cycle, and the records that flagged `introduced_by_fix` or `recurring`.
- **Cases are listed, not discovered.** Coders patched the line a finding cited, and siblings like `size=None` then surfaced one review cycle at a time, because no one ever wrote the case family down. Now each plan task carries a `Cases:` line: every case its rule covers, with the intended behavior, or `n/a — <reason>`. `task_brief.py` refuses a task without it. The spec reviewer checks that each listed case has a test, a yes-or-no question rather than a judgment. When review still finds a missed case, the finding names the rule and its whole class, and the fix is held to the class, not the cited line.
- **Fixes diagnose before they patch.** The fix re-dispatch points at the coder's same record path; the coder reads its prior record and self-derives `cycle` as prior + 1 — and from cycle 2, `ledger.py check` requires a `diagnosis` (`root_cause`, `end_state`, `resolves_cluster`). A cluster of findings usually shares a cause; N local patches leave the cause intact and create fresh inconsistency at the seams. The re-reviewers then judge the fix against its own stated cause: closing the listed sites while the stated root cause stands is a finding, not an approval.
- **Recurrence, not new findings, is the failure signal.** Re-reviewing agents compare against their own prior record and emit `recurring` — the same finding class at the same site across cycles. New findings after a fix are often *discovery*, not failure: wiring a dead parameter makes its missing validator reachable, and taxing that expansion would punish the loop for working. When `recurring` fires, the previous mechanism has demonstrably failed, and the next decision doc must say why and choose a different one, weighing at least two candidates.
- **The third non-trivial fix belongs to the user.** A task gets at most two non-trivial fix attempts. The orchestrator flags each one's baseline snapshot `--non-trivial`, and `ledger.py fix-count` counts them; cycle numbers aren't the count, since trivial fixes advance a coder's cycle and a re-dispatched reviewer advances its own. A non-trivial finding still open after two non-trivial fixes escalates (trivial leftovers just get fixed). When the records show the recurring-mechanism signature persisting *through* a decision-doc fix, the orchestrator attaches the decision docs as the escalation's briefing, so the user decides between researched options instead of debugging the loop. Every other escalation signature (spec ambiguity, reviewer conflict, scope) escalates directly: those need adjudication, and research would only delay it. A reviewer finding closes only when a re-review stops raising it or the user waives it. When a decision doc concludes a finding can't or shouldn't be fixed as asked, it escalates to the user with that evidence and stays out of triage and the fix count until the user rules; the orchestrator never closes one by its own ruling. The user's ruling is logged in the store, and a logged waiver is the one instruction reviewers accept for dropping a finding.

Round count is the wrong metric for this loop — re-reviews on changed surfaces legitimately catch real regressions. The waste metric is narrower: rounds where a fix failed to close its own finding, or where a finding was available earlier but delivered late. The rules above target exactly those.

## The close round

The completion close (`verification-before-completion`) has its own loop, and before this rule it was the ungoverned one. Its gates (design review, intent re-check, mutation) ran one at a time with a fix after each, so a design fix was followed by intent findings on the patched code, then mutation findings, and every behavioral fix reopened the gates before it. Those fixes also skipped the coherence engine entirely.

A **close round** dispatches every applicable gate at once, waits for all of them, and triages once. Trivial findings are fixed inline. A discriminating-test fix for a mutation finding goes straight to the coder. Separable improvements are logged. The non-trivial set goes through `remediating-issues`' close-gate variant as one batch: one consolidated research pass and decision doc, which pauses for your approval (unlike the per-task variant, which runs continuously), then straight to one `lean-plan` (no `lean-spec`, since the gate reports already say what is wrong) and SDD on the same store. Round 2 re-runs only what the remediation could have changed: the design reviewers at their same report paths (so each judges whether its prior findings were addressed instead of re-deriving the whole change), mutation over the remediation's range only, and the intent re-check only when the remediation changed behavior. A new finding on code the remediation never touched counts as fresh sampling, not a regression, and is logged as a follow-up. Whatever non-trivial work survives round 2 goes to the user. `ledger.py close-round --expect N` keeps the count as a typed entry and refuses a third round, so the cap survives compaction. `--expect` also fails when the store disagrees with the round you think you're starting, so a store left by an earlier run can't silently start a new close at round 2.
