# Ledger commands

`ledger.py` is the typed record store behind `subagent-driven-development`, `executing-plans` and `verification-before-completion`. It lives in the SDD skill's `scripts/` directory and is always called through `$SDD_SCRIPTS`, the skill's absolute scripts path. Every command except `diff-since` and `labels` takes `--store DIR`; the default store is `.sdd/` at the repo toplevel.

Commands that write the store hold an exclusive lock on its `.lock` file while they read, check and write, so parallel agents never interleave lines or both pass a check only one of them should. The store doesn't exist until its first write (normally `store-dir`), and only that write runs unlocked. A refusal writes nothing, not even the store.

Records carry schema version 2. A record or store written by an earlier release is refused with a message to finish that run on the release that started it, or to `clear` the store and start over.

## Reading the run

| Command | What it prints |
|---|---|
| `run-state [--plan PLAN]` | First a `Verdict:` line and a `Next:` line: whether the store is `fresh`, a run of this plan to `resume`, a close in progress (`closing`, naming its latest step), a `finished` run, another plan's (`foreign`), or `ambiguous`, and what to do about it. Without `--plan` it judges against the latest plan the store recorded; a `--plan` that doesn't exist exits 2. Then where the run stands: the run's settings once any is recorded (`run-config`), the stage map with each task's state, each task in flight's rounds so far, what's parked for the stage's batched question (an inline offer awaiting the user's answer, an escalation, a held or waiting finding, an open behavior choice), notes owed, open disclosures and questions, the count of blocking items, agent handles, the latest checkpoint, and once the close starts, its steps, rulings and deferrals |
| `read` | The whole store as markdown: every record, then every progress-log entry |
| `open` | What blocks: open record items (`cannot_verify`, each with the action that settles its kind; `duplication_pending`, escalations, open statuses, a `handed_off` coder whose coder of record hasn't finished that cycle, malformed records), notes tasks in flight haven't received, and open disclosures and questions. A `cannot_verify` item whose recorded command result the scope's files have moved past is listed again |
| `completed` | Task ids with a completion entry, one per line |
| `shapes` | Shared symbols the coders declared, as every brief carries them: one line per symbol and path, credited to the earliest task that declared it |
| `stats` | Each task's verdicts cycle by cycle from the check history, the records that flagged `introduced_by_fix` or `recurring`, each triage round by task (kind, coder model, and how many findings it closed, saw survive and saw a fix introduce), and the tests-first `n/a` counts by category |
| `report` | What the completion report lists: user rulings, the open follow-ups grouped by rule as the close batch (fix, file or ignore each), the coders' `unlisted case:` concerns, follow-ups settled during the run, dispositions and waivers, disclosures with where each landed, questions with their rulings, and the tasks that ran light |
| `notes --task N` | The notes task N must receive, marked delivered or not, and the questions it owns |
| `findings <decision-path>` | The finding ids a holistic decision record at that path must account for, and the decisions it must reconcile with |
| `baseline <tree> --task N\|final\|close` | The round a fix baseline starts: its kind, its cycle (the one every coder of the round writes), who re-checks it, the decision doc path for a holistic round, and the findings sent. Errors when the last triage entry before that snapshot isn't a fix round, and while the round is an inline offer the user hasn't answered |
| `store-dir` | The resolved store path, creating it and its self-ignoring `.gitignore` if needed |
| `path --task N\|final\|close [--agent NAME] [--kind record\|report\|brief] [--item ID]` | A handoff file's path: `task-N-<agent>`, `final-<agent>`, or `close-<agent>` for the close's gates and coders, as `.json` for a record and `-report.md` for a report; `--kind brief` gives `task-N-brief.md`. `--agent claim-checker --item <id>` gives the record path for that `read` item, `<scope>-claim-<digest>.json`. Exits 2 on a combination with no file (a brief outside a task, an agent name with a path in it) or a retired scope (`gate`, `ruling`), whose message names `--task close` |

## Routing a task

| Command | What it does |
|---|---|
| `triage --task N\|final\|close` | Turns the scope's records into state changes for its findings, computes the next step (`patch`, `holistic`, `ruling`, `polish`, `escalate` or `decide`, `clarify`, `done`) and prints it, with who re-checks it and, for a fix, the `Fix baseline`. Refuses, writing nothing, while a record in scope is malformed or when the scope has no reviewer record. See [`triage` in detail](#triage-in-detail) |
| `ready --task N\|final [--light]` | Lists every blocker to a commit and exits 1 while any remains: triage not at `done`, a held or waiting finding, a finding still awaiting its re-check, an open behavior choice, an undelivered note, an open disclosure or question the task owns, an inline offer the user hasn't answered, an open `cannot_verify` item (never one whose command is `gate`, which the commit itself settles), a first attempt's handoff whose coder of record hasn't finished, a malformed record, and at `final` an open escalation or `duplication_pending`. A task's own decision escalations aren't open items: the coder contests them. `--light` is executing-plans' path, which runs no triage, and skips the checks that read it: the triage step, held and waiting findings, re-checks, an inline offer and open choices |
| `gate --task N\|final [--test CMD] [--lint CMD]` | Stages every change under the scope's footprint (at `final`, every task's files plus the files its coders changed), runs labels on the staged lines, then lint, then the task's `Verify:` command, each passing only on exit 0, and writes a gate record. With no `--test`, a task's test is the `Verify:` command its brief recorded, and at `final` the run's full suite (`run-config --test`); with neither on record it exits 2 and runs nothing. With no `--lint`, the lint command is the run's (`run-config --lint`), and `--lint ""` runs none. Before running each command the gate prints it with where it came from (this command line, the task's brief, or `run-config`). Everything a lint or test command printed is kept in the store (`<scope>-gate-lint.log`, `<scope>-gate-test.log`), and the record names the file. The record's excerpt is the command's last 20 lines; a failed command's excerpt leads with up to 15 earlier lines that look like the failure itself (`FAILED`, `error`, `panicked at`, a traceback), and the gate prints it with the log's path. The commands run through `/bin/sh`, and one that names a program that shell can't find fails whatever it exits with (`! rg -q x` exits 0 where `rg` is missing, having searched nothing). Only that shell's own report counts: a script the command runs may meet a missing program and handle it. Refuses when the scope has no recorded footprint, or a task's footprint has no change (at `final` and `close` it gates HEAD instead). The test finding's text never carries the run's output, so the same failure keeps its id. Exits 0 on pass, 1 on fail. A labels or lint failure returns to the coder as the same attempt. A test failure becomes one S3 local finding over the scope's files and enters triage |

### `triage` in detail

`triage --task N|final|close` turns the scope's records into state changes for its findings, then computes the next step.

**Finding states.** Every finding is its own run of `finding` entries in the progress log, and its state is its latest entry: `fix`, `sent`, `held`, `waiting`, `note`, `noted`, `filed`, `fixed` or `dropped`. Only a re-check changes a finding:

- One seen for the first time starts as `note` (S1-S2), `filed` (S1-S2 of contract reach, filed as a follow-up) or `fix` in a task, and at the close as `fix` (an intent not-met, S4+, or a failing commit gate) or `waiting`.
- After that a record only reports what a re-check saw: a sent finding its rewritten record no longer raises is `fixed`, one still raised is `fix` again, and a contest the raising reviewer concedes is `fixed` and one it holds is `held`. After a round fixed inline, the coder record's contests speak for an earlier round, and their answers are ignored.

**The step.**

- `patch` or `holistic` (contract reach or a `root cause:` concern) sends the `fix` findings.
- After two such rounds, or after a ruling round, open work goes to the user as `waiting` instead, and the step is `escalate` in a task or `decide` at the close, the same step that comes when only held or waiting findings remain.
- A finding the user rules `fix` after either starts a `ruling` round, and in a task so does an override logged since an `escalate` or `done` entry. A ruling on the mutation gate starts no round.
- A task's notes or an undelivered note get `polish`; otherwise the step is `done`.
- At the close an open can't-tell prints `clarify` (re-check `intent`, no round, no snapshot), and `done` is final.
- A `root cause:` concern a decision chooses to fix (once its round's fix finishes, unless the user discards it) or excludes, or the user waives, stops counting.

**What it writes and prints.** It appends the state changes and one triage entry, and files the loop's deferrals as follow-ups (S1-S2 contract-reach findings, notes a coder skipped, sites a sweep found outside the scope, root causes a decision excluded). It files each `elsewhere` item a spec reviewer raised the same way and logs the item settled: a task-note when an unfinished task's footprint holds one of its sites, a follow-up otherwise. It prints the step, who re-checks it (`raising`, `all`, `spec` after an override's ruling round, `gate`, or `none`), each sent finding's id, tier and rule, the held and waiting findings with the `rule` command that settles them, the decision doc a holistic round writes, a re-run-the-gate line when a gate finding was sent, and the settled ids. A fix step (`patch`, `holistic`, `ruling`, `polish`) also snapshots the working tree right after its entry and prints `Fix baseline: <tree>` and `Task files: <paths>` for the dispatch.

**Inline.** A `patch`, `polish` or `ruling` step whose every finding is one site (reach `local`) of S3 or less, none a gate's or an intent not-met, and with no `root cause:` concern, overridden behavior choice or undelivered note beside them, is marked `inline`: an offer to the user, who says whether the coder or the orchestrator fixes it. Triage's first line says so: to park the task for its stage's batched question, or at `final` and the close to ask the user now. The round waits for `inline --by` before anything else: nothing but that answer, or a ruling that ends the round, moves it. A round an earlier release marked `inline` and already finished, by a coder or inline, needs no answer.

**How long a round lasts.** A fix step's round lasts until all of these hold:

- an inline offer has its answer, and the fixer the user named has finished: the coder (a `done` coder record carries its baseline), or the orchestrator (`inline --done` from that baseline);
- at `final` and `close`, `commit` has landed the fix;
- the raiser of each finding it sent has written its record again (a re-check, or a new `gate` run for a gate finding), as has every other record it named (every reviewer after a holistic round, the spec reviewer after an override's ruling round).

A round whose every sent finding (a polish round: its notes) the user has filed or dropped waits only for `discard` of its unlanded changes. Until then, or with nothing changed, triage reprints that entry and its baseline with what it is waiting for and logs nothing. A record counts as re-checked by being written, so a re-check with the same content still counts.

**An older store.** A store triaged before findings had entries is seeded from its triage entries once.

## Writing the run

| Command | What it does |
|---|---|
| `note --kind KIND --text "..." [--for N] [--owner N\|close] [--from N\|final\|run] [--rule TEXT]` | Files an orchestrator note and prints its id. Kinds: `task-note` (`--for` a task), `run-note`, `disclosure` and `question` (`--owner` a task or `close`), `follow-up` (`--rule` is the rule it falls under, which `report` groups by), `disposition`, `checkpoint` |
| `notes --task N --deliver` | Records that the session (not a brief) delivered every note the task requires |
| `notes --task N --waive ID --reason "..."` | Records that a required note doesn't apply to the task, with why |
| `run-config [--plan PLAN] [--spec SPEC] [--test CMD] [--lint CMD]` | Prints the run's four settings, after recording any given: the plan and the spec that `brief` builds from, the project's full test suite (the gate's test at `final` and the close) and its lint command. A later call replaces only the settings it names, and an empty value unsets one. `--plan` and `--spec` must name files, and `--plan` also records the plan as the run's, which `run-state` judges against. `run-state` lists the settings |
| `brief --task N [--intent "..."] [--coder NAME...]` | Builds the task's brief by running `task_brief.py` at the repo root on the recorded plan and spec, with the plan's Constraints section when it has one. Prints `brief: <path>`, then `<agent> record: <path>` and `<agent> report: <path>` for each coder named, the spec reviewer, and each coder's quality reviewer (`python-coder`, `pytorch-coder` and `rust-coder` have one). `--intent` is needed the first time; a rebuild reuses the last. Exits 2 with no plan on record or no intent, and with `task_brief.py`'s own status (2 or 3), printing no path, when it refuses the task |
| `stage --task N --stage K --files PATH...` | Records a task's stage and file footprint; refuses a path another unfinished task in the same stage claims. `stage --task final --files PATH...` (or `--task close`) adds files to that scope's footprint, for a fix outside every task |
| `stage --task N --extend [PATH...]` | Adds to a numbered task's recorded footprint the paths given and every file its coders' records list as changed, and prints what it added. The task keeps its stage unless `--stage` gives another, and a path another unfinished task in the stage claims is still refused. Refused for a task with no footprint yet, at `final` and the close, and together with `--files` |
| `handle --task N\|final\|close --role NAME --agent ID` | Records the agent id behind a task's role, so it can be continued after a compaction |
| `commit --task N\|final\|close --message "..." [--test CMD] [--lint CMD] [--light]` | Takes a ready scope to a completed commit and exits 1 at the first step that stops it: the `ready` blockers, the footprint check, the gate (with `gate`'s own defaults for `--test` and `--lint`), `git commit` of the footprint alone, then `complete`, which settles the scope's `gate` items and releases a scratch lease still held for it. At `final` and `close` it also commits each finished fix for its re-check. See [`commit` in detail](#commit-in-detail) |
| `append --type progress\|complete --task N\|final\|close\|run --note "..." [--light]` | A progress note or a task's completion (`commit` appends the completion itself). `--task close` is for rulings about the close (the mutation-gate answer; its findings are ruled with `rule`), and `--task run` for rulings about the whole run. `complete` re-runs `ready` and refuses without a passing gate whose staged tree matches the committed blobs of the scope's files. `--light` is executing-plans' path and is recorded on the entry, so `report` shows which tasks ran light. `--type complete --task close` is refused: the close finishes when its triage prints `done` |
| `rule ID... --as fix\|file\|drop --note "user ruling: ..."` | Records the user's ruling on reviewer or gate findings, in a task or at the close, as each finding's next entry. `fix` puts it back to be fixed (the next triage starts a ruling round), `file` files it as a follow-up carrying its id, raising record and report path, and `drop` settles it. A later ruling replaces an earlier one, and moving a finding off `filed` resolves its follow-up. Checks every id before writing anything, and refuses an id no record in scope raised, a finding already fixed, `fix` on a finding a round has already sent, a finding of a completed task, and any finding once the close is done. A finding a record raises that triage hasn't seen yet takes its data from the record |
| `inline --task N\|final\|close --by coder\|orchestrator --note "user ruling: ..."` | Logs the user's answer on who fixes the round triage marked `inline`. Until an answer is logged the round waits: `triage` prints the offer first, `baseline` refuses the round, `check` refuses a coder's fix for it, `ready` lists it and `run-state` shows the task parked on it. With `coder` the round runs like any other; with `orchestrator`, `check` refuses a coder's fix for it. A later answer replaces an earlier one until the fix finishes, and an answer covers the scope's latest round only: the next offered round is asked again. Refuses a step triage didn't mark `inline`, a round already finished or ruled off, and a note that isn't the user's ruling. `report` lists it with the rulings |
| `inline --task N\|final\|close --done [--files PATH...]` | Logs that the orchestrator fixed the round itself, as the user answered. It finishes the round as a coder's finished fix would, and the next fix step's cycle comes after it. The commit (at `final` and the close) and the re-checks follow as for any fix, and the round counts toward the cap. Refuses what `--by` refuses, a round the user hasn't given the orchestrator, and a fix that changed nothing since the round's baseline. `--files` names the files the orchestrator changed: one outside the scope's footprint joins it at `final` and the close, and is refused in a task, whose footprint grows by `stage` |
| `discard --task N\|final\|close` | Ends a round the user ruled off (every finding it sent filed or dropped): puts the files it changed and never landed back to the round's `Fix baseline`, so the work before the round stays, removes the scope's gate record, which judged the discarded work, and logs the discard. Refuses a round that still has work, and one with nothing to discard |
| `resolve ID [--note "..." \| --run COMMAND]` | Closes an open item or note. Escalations and questions need `user ruling: ...`, and so do an intent statement still can't-tell (`close-intent-reviewer#statements[<n>]`), a coder's open behavior choice, and a coder's `root cause:` concern, which only the user settles (waived, accepted or overridden). A reviewer or gate finding is refused: the user rules it with `rule`. A disclosure's note says where it landed. A typed `cannot_verify` item takes no note but the user's ruling; see [`cannot_verify` items](#cannot_verify-items) |
| `snapshot --task N\|final --label "..."` | Records the working tree as a fix baseline and prints its tree id, for a fix outside triage (executing-plans). `triage` takes an SDD or close fix's baseline itself |
| `close-round --note "..."` | Starts the completion close and prints the HEAD its gates review. Refuses when the store already holds a close (an unfinished one resumes at triage; a finished one is final, and a new close needs a cleared store), and while any disclosure or question is open or a task-note waits on a task that never completed. Its rounds are counted by `triage --task close`. The retired round-number flag fails with the new usage |
| `check <record-path>` | Validates a record an agent just wrote and appends its summary to the check history. It enforces each role's contract, including a finding's severity, reach, rule and sites, a re-check's answer to every forwarded contest (none after a round fixed inline), a fixed finding raised again unchanged (one the user dropped or filed may be; `reopens` must name a settled finding and sit in code changed since), a coder's shared symbol listed twice, a `handed_off` coder with no other coder named in `handed_to`, a fix record (a `handed_off` share included) without its baseline or below its round's cycle, a coder's fix for an inline offer the user hasn't answered or gave to the orchestrator, and, on a finished fix, the sweep rows, tests first (an `n/a` entry names a test only when its category is `existing`), decision rows and test changes the round required. On a spec reviewer's record it refuses a `cannot_verify` entry that doesn't say what settles it, and on a claim-checker's record a quoted line that isn't that line of the file, or evidence that shows nothing (see [`cannot_verify` items](#cannot_verify-items)) |
| `clear [--discard-open]` | Deletes the run's records, handoff files and logs, and the run's scratch copy, build cache and lease. A command still running in the copy is stopped first; if it doesn't stop, `clear` warns and leaves the scratch folder. Refuses while follow-ups, disclosures or questions are open, unless the user confirmed the loss |

### `commit` in detail

`commit --task N|final|close --message "..." [--test CMD] [--lint CMD] [--light]` takes a ready scope to a completed commit and exits 1 at the first step that stops it. In order:

1. the `ready` blockers (nothing staged);
2. the test command: with no `--test` and none on record for the scope (`gate`'s defaults), it exits 2 with nothing staged;
3. a coder file outside a task's footprint, which `stage --task N --extend` adds;
4. the gate (skipped when the last passing gate checked these same files);
5. `git commit` of the footprint alone with the message verbatim (other staged paths stay staged);
6. `complete` with `commits <before7>..<after7>`, which settles the scope's `gate` items and releases a scratch lease still held for the scope. The copy and the build cache stay for the run's other tasks.

**At `final`,** a fix the coder has finished is committed for its re-check without `ready` or `complete`, and at `done` with nothing left uncommitted it gates HEAD and completes without a commit.

**At `close`** it commits only a finished close fix, for its re-check, and completes nothing: the close finishes when its triage prints `done`.

**A fix's commit at `final` and `close`** logs the files its coder changed into the scope's footprint (so a file from an earlier attempt stays in) and logs the fix as landed, which its triage waits for. A failing gate there goes back to the coder as the same attempt (to the orchestrator, after an inline fix), and a fix that changed nothing lands without a commit once the gate passes on HEAD.

**Skipping the gate.** The gate is skipped only when the last passing gate checked the same files, staged the same way, with the same test and lint commands; a file the gate's commands rewrote stops the commit until it is gated again.

**A refused `complete`** after the commit reports the commit, which is never undone.

### `cannot_verify` items

A spec reviewer's `cannot_verify` entry says what settles it, in `needs`, and the ledger accepts nothing else for it but the user's ruling (`resolve ID --note "user ruling: ..."`).

| `needs` | The entry carries | What settles it |
|---|---|---|
| `run` | `command`: `gate`, or a shell command | `gate` is the scope's own `Verify:` command: the item never blocks `ready`, and `complete` logs it settled with the gate's commands. Any other command is run by `resolve ID --run COMMAND`, at the repo root, by the gate's rules. A reviewer wrote the command, so it runs only when `COMMAND` repeats it exactly: the caller's own command line then shows what runs. On a pass the resolution records `exit`, the working tree's `tree` and the output's `tail`. On a failure nothing is recorded and the output is printed |
| `elsewhere` | `sites` outside the scope's files | `triage` files it and logs it settled |
| `read` | `claim`, `path`, `lines` | `resolve ID` with no note, once claim-checker's record for the item passes `check` with status `holds`. `does-not-hold` and `not-decidable-by-reading` are refused, naming who settles it next: the spec reviewer, or the user |

- **A run result goes stale.** It stands for the tree it ran on. Once a file of the scope's footprint differs from that tree, the item is open again and `resolve ID --run COMMAND` runs the command again. A completed scope's results stand.
- **The claim record** is role `claim-checker`, with the verdict as its `status`, the `item` id, an `evidence` list (`path`, `line`, `text`; 3 to 10 lines unless the status is `not-decidable-by-reading`) and one sentence in `because`. `check` compares each quoted line with that line of the item's file in the working tree, ignoring the whitespace around it and numbering lines by newlines alone, as an editor does. It also refuses evidence that shows nothing: a line quoted twice, a blank line, or no line inside the item's `lines`. `resolve` checks the record again, so one edited after its check, or whose quotes no longer match the file, settles nothing.
- **An entry with no `needs`** is one an earlier release wrote. It loads, and `resolve ID --note "..."` closes it as before; `check` refuses a new one.

## Reading the working tree

| Command | What it does |
|---|---|
| `diff-since <tree> [<path>...]` | The diff since a snapshot tree, new files included, limited to the task's files |
| `labels <tree> [<path>...]` | Lists review-process labels (task and finding ids, cycle numbers, commit hashes) on lines added since the tree; exits 1 if any |
| `scratch take --task N --agent <name> [--wait SECONDS]` | Gives the run's one scratch copy to a quality reviewer for its break check and brings it to the working tree as it is now (uncommitted edits and new files, not edits inside submodules). The copy is a throwaway worktree in the system temp folder, outside the repo and the store, so a build cache never lands in a synced folder (a `TMPDIR` inside the repo must be one git ignores, or it's refused). The per-user folder there must be one only this user can write to: a symlink, another user's folder, or one others can write to is refused. An existing copy is updated in place through git, which rewrites only the files that differ and stamps them now, discards every edit left in the copy and keeps the files git ignores. Prints the copy's path, the `scratch run` form, and the run's limits. While another reviewer holds the copy it waits (90 seconds by default), then exits 3 naming the holder. The same holder may take it again, unless a command of its own is still running in the copy, and a lease with no command running and none for 20 minutes is taken over. A take that can't bring the copy up to date gives back a lease it just took. The checkout is never touched |
| `scratch run --task N --agent <name> -- COMMAND...` | Runs the command at the root of the copy for the reviewer that holds it, with the run's build cache set (`CARGO_TARGET_DIR`), and passes its output and exit status through. A guard stops the command's whole process group past the run's time or memory limit: exit 124 for time, 125 for memory. Exit 126 means nothing ran: the caller doesn't hold the copy, an earlier command of its own is still running there, or the command couldn't start. Whatever the command leaves running is ended when it returns. The guard is a process of its own, in its own session: when the call is terminated it stops the command (exit 143), and when the call is killed outright it keeps the command under its limits until it ends. The lease marks the guard and its command by process id and start time. If the guard itself is killed the call also exits 143, and ends the command the guard left running before it returns. When the call is gone too, the next scratch command that reads the lease ends that command |
| `scratch release --task N --agent <name>` | Gives the copy back. The copy and the build cache stay for the next reviewer. Releasing a copy you don't hold changes nothing, and releasing one a command of yours still runs in is refused. A task's commit releases a lease still held for it; one with a command still running is released when that command ends |
| `scratch limits [--time SECONDS] [--memory GB]` | Prints the run's limits on one `scratch run` command, after logging a change to them. The defaults are 540 seconds (under the ten minutes a foreground tool call may run), and 12 GB or half the machine's memory, whichever is less. The limits are the run's, set by the orchestrator: `scratch run` takes none |

`task_brief.py`, beside it, builds each task's brief from the plan, embeds the task's notes from the store, logs their delivery, and records the plan in the store once (what `run-state` judges against). It also logs the intent the brief was built with, which a rebuild through `brief` reuses. With it, it logs the task's `Verify:` command when the task's `Verify:` lines name exactly one backticked span between them, which the task's gate then runs; with several spans it logs none, and the gate needs `--test`. `ledger.py brief` is the usual way to run it. With `--spec`, it refuses a plan without a `Spec coverage: <that spec> — pass (<report>)` line (or a `user ruling:` form) whose report exists, the record of lean-plan's coverage check. It refuses a task whose `Verify:` line has no backticked command, whose `Cases:` still carries an `open:` row, or whose `Cases:` has a row that doesn't separate its situation from its expected result with `→` or `->`. A row may group cases (`size=0, size<0 → ValueError`), and `n/a — <reason>` and the refactor form (`preserves <behavior>; covered by <tests>`) are exempt. It also opens the brief with the task's rigor level, and refuses a task `Rigor:` line below the project level.

`rigor.py`, beside it, resolves the test rigor level (see `rigor.md` in the skill directory for what each level changes). It reads tracked files only and writes nothing.

| Command | What it prints |
|---|---|
| `rigor.py [--repo DIR]` | The project level and its reasons, e.g. `standard: 4,200 source lines (python); numpy +1` |
| `rigor.py --plan PLAN --task N` | Task N's level: the project level, or the higher one its `Rigor:` line sets |
| `rigor.py --plan PLAN --store STORE --files` | The project line, then `<level> <path>` for each file a raised task's latest stage footprint lists |
